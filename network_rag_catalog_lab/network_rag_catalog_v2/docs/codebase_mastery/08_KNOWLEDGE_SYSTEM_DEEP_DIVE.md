# Knowledge system: authoring versus runtime

Do not read `app/knowledge/*` as one execution path. The default terminal runtime is direct `data/`; the management backend is a separately available authoring/publication path. `config.runtime_mode()` decides runtime (`files` default, `published` explicit). `authority.authority()` independently decides authoring store (`json` without marker, `sqlite` with a valid marker); this workspace may be SQLite-backed for authoring while `main.py` still reads direct files.

## Authoring path

`knowledge.cli.main` or a future API can call `KnowledgeManagementService` (`management.py`); `api/contracts.py` defines typed edit/import/publish requests and structured results, but no HTTP controller exists here. `management.inspect` reads revision/counts/active release. `apply` parses an `EditRequest`, checks expected revision, applies changes to a copied full catalog via `_change`, checks published-deletion safety and `_validate`, then calls the selected store's `commit` with actor/reason. `dry_run` returns impact without writing. `preview_schema`, `validate`, `export`, `import_catalog`, `publish`, `migrate_sqlite` and `recover` have distinct entry points.

`authority.authoring_store` chooses `JsonAuthoringStore` or `SQLiteAuthoringStore`. SQLite code (`sqlite_repository.py`) stores typed catalog rows plus JSON payloads in tables from `migrations/001_authoring.sql`; `_replace_catalogs` replaces the complete catalog in one transaction, foreign keys are on, `commit` uses `BEGIN IMMEDIATE`, revision check, generation increment and audit row. `migrate_to_sqlite` requires an active baseline release, validates a JSON snapshot, backs it up, loads SQLite, verifies equality, then atomically writes `authority.json`. A missing marker with an existing DB is an error, not silent JSON fallback. `FileKnowledgeRepository` remains important for direct-file reads and released catalog reads; `DocumentKnowledgeRepository` reads an in-memory catalog bundle; `SQLiteKnowledgeRepository` exposes a typed DB snapshot.

`models.py` owns typed Category, ParameterDefinition, CategoryParameter, Operation, OperationParameterMapping, OperationSchemaRule, TemplateBinding and vendor-knowledge records. `services.py:KnowledgeService` validates cross-record references/memberships and offers stable ID lookups. `operation_contracts.py` projects/compares normalized mappings with legacy schemas. `migration.py` backfills membership/mapping suggestions. `schema_compiler.py` composes mappings and rules into JSON Schema, checks keyword applicability and handler IDs. `rule_registry.py` allows only reviewed Python validation/normalization/derivation handlers; catalog data cannot import arbitrary code.

`pack_review.py` reads hashed pack manifests, checks non-overwriting assets, prepares idempotent management changes, and rehearses in a disposable project. `pack_promote.py` processes reviewed packs/inventory additions with backup and receipt; it is not a runtime dependency. `vendor_coverage.py` reports/validates reviewed vendor declarations; `resource_keys.py` handles composite resource identities. Pack presence does not mean an operation is live.

## Publication path

`management.publish -> publication.publish` locks publication and authoring, checks active-release and authoring revisions, assembles source assets (SQLite-managed catalogs override seed JSON), validates metadata/mappings/schemas/bindings/context rules and operation version bumps. It writes compiled base/profile schemas, reviewed template copies and retrieval documents into a staging directory. In `chroma` mode `ingest.build_release_index` creates `knowledge_<release_id>` and verifies all IDs/content; only then does `publish` finalize the release and atomically replace `active.json`. A failed stage is not activated. In `offline` mode no semantic Chroma retrieval is available. `publication.build_documents` is the published retrieval text builder; `file_runtime.file_documents` is the different direct-mode builder.

## Runtime path

`runtime.current_snapshot` returns `None` in files mode and `KnowledgeSnapshot` in published mode. `snapshot_request`/`snapshot_scope` keep a request on one snapshot. `catalog.knowledge_service` chooses snapshot service or direct-file service. `schema_loader.load_schema`, `template_selector.select_template`, `context.rules`, `vectorstore.get_vectorstore` branch on that snapshot. `KnowledgeSnapshot.verify` hashes artifacts; `assert_active` rejects a changed active pointer. Inventory/planned context remains local `data/` in both modes and contributes to `context.source_revision`. In published mode, SQLite is **not** read on every prompt; the immutable release is.

## Important disagreements with older prose

Some phase notes call SQLite “authoritative” without distinguishing authoring authority from terminal runtime. Current `config.py` makes `files` the default. Some older notes discuss explicit bindings as if every terminal template lookup uses them; current `template_selector.template_binding` returns `None` in files mode. Follow current source when debugging, and ask which mode was used before comparing two outcomes.
