- **Inventory mutability:** Iteration 9 adds only synthetic registration, including optional initial interfaces, to the existing uncached JSON authority. Complete proposed-record/identity/reference validation, logical-revision conflicts, partial-write/fsync/replace failure safety and actual V9 target discovery are tested. Old records retain all original attributes; successful saves reformat JSON. The shared process gate excludes planning/answers during writes; the final revision check is not cross-process CAS. No edit/delete, backup/undo feature, external-writer coordination or power-loss/OneDrive conflict guarantee. A timed-out registration may have saved: reload and inspect before retry. Raw device-ID prompt selection is unsupported by current V9, while inventory detail GET accepts IDs.
- **FYP reuse quality:** Source audit completed. Small input/icon reuse and layout/editor-pattern adaptation are recommended. Broad controllers, inventory synchronization endpoints and old intent/execution logic are excluded. Dependency/build/security certification remains outside the audit.
- **Monaco completeness:** The shell now builds and loads a local Monaco worker with distinct model paths for each in-memory sample tab. Persistent generated/draft records, DiffEditor integration, arbitrary edited-content validation, and production bundle splitting remain future work. The current production bundle emits a greater-than-500-kB chunk warning.
- **Frontend dependency advisories:** The production dependency audit reports two low-severity DOMPurify advisories inherited through Monaco 0.57.0 and no high-severity production advisory. Do not use a forced downgrade/fix without a separately verified compatibility decision.
- **Contract design:** Creation and answer POSTs retain complete V9 payloads and saved-byte hashes. Answer mutation validates expected saved/question/source revisions. Iteration 7 adds passive GET using the same lossless saved-payload validator, with historical authority preserved and freshness/mutation eligibility `not_checked`. Explicit resume and artifact/draft services remain unimplemented. V9 still has no shared CLI/API cross-process CAS or arbitrary edited-configuration validator.
- **Mutation retries/timeouts/persistence:** Creation and answers still share one process-local gate and a combined 256-ID cache. Iteration 8 adds durable creation receipts under configured session storage: intact completed receipts prevent recreation across restart; accepted-but-unfinished receipts block replay as indeterminate. A post-save/pre-completion-receipt crash was explicitly tested. This is not exactly-once execution or automatic reconciliation. Multiple workers, independent CLI writers, filesystem loss/tampering and sudden power-loss durability remain unsupported. The 120-second browser timeout does not cancel V9. Answer outcomes remain process-local; exact history evidence can identify a recorded answer, not its HTTP request. Missing evidence keeps new answers blocked.
- **Creation receipt capacity/retention:** Receipts are capped at 4,096 bytes each, with 1,024 directory entries (including orphan temporaries) before new acceptance is refused. No automatic eviction, expiry or repair is performed. Preserve receipts together with sessions during backup/restore; removing a receipt destroys its restart deduplication evidence. Missing records mean unknown, not proof of no prior side effect. Pre-Iteration-8 creations have no receipts and are not backfilled or guessed.
- **Clarification rejection/recovery:** V9 can save rejected history and feedback. The adapter distinguishes no-write precheck errors from `V9_ANSWER_REJECTED`, which includes the confirmed updated saved state/revision. Only explicit user review enables a changed-value retry with a new ID. Source/session staleness cannot be recovered through a general GUI resume workflow yet. Legacy/incompatible session formats are rejected, not migrated.
- **Recovery scope:** Only minimal session ID/revision/answer-uncertainty and unconfirmed creation UUID metadata is retained in browser storage. Iteration 8 lets the user explicitly check that UUID, then separately GET and adopt a validated completed saved session as historical state. No automatic POST/GET, replacement UUID or older-session guess occurs. Unknown, corrupt, terminal-error and indeterminate outcomes retain the request reference. Browser storage may be unavailable/cleared; answer evidence is still lost on reload. Explicit resume, historical browsing and durable answer receipts remain deferred.
