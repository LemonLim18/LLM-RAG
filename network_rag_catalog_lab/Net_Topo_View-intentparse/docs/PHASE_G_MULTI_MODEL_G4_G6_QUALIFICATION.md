## Failure boundaries and provenance

1. **Source/execution boundary:** the original remote role plan could add configuration/topology to an explicitly state-only request. Eight answers explained the right causal facts but still violated source instructions. This is a planner selection error compounded by missing server enforcement, not evidence that those correct explanations were overwritten. MMQ20's Qwen plan actually selected saved configuration correctly, but a legacy protocol alias remapped it to state; wrong operands then reached Qwen. A role-eligibility gap also prevented escalation for two distinct sentences and one same-device time comparison.
2. **Completed reasoning with supplied operands:** MMQ17 attributes OSPF mismatch partly to unequal local process IDs; MMQ24 claims planned links confirm usable connectivity despite unavailable observations; MMQ29 treats a simulated2-Way adjacency as physical/data-link proof. MMQ16 adds an incorrect device identifier. Other partial answers omit a requested VRF comparison or blur branch/direction relationships. These are model interpretation/completion failures with evidence present. They are not provider failures or justified universal-verifier claims.
3. **Sufficiency decision:** MMQ27 received the initial requested saved/topology evidence and discovered relationships, but chose `answer` without the additional state needed for the causal task or an adequate missing-evidence assessment. MMQ28 legitimately prefetched both configuration scopes; direct completion is allowed and is not adaptive-round evidence. None of the original completed decisions used the supplementary branch.
4. **Provider/contract failures:**503s occur at reasoner cases02/07/12/14 and planner30; planner26 times out. No answer was generated at those stages, so no reasoning inferiority is inferred. The invalid MMQ25 enum is a completed-model contract failure, correctly rejected before execution.
5. **Evaluation defect ED-01:** current-configuration fixture rows were authored with `kind=configuration` instead of the current reader's `running_configuration` kind. MMQ02's exclusively current read is empty; MMQ25's local setup is affected. Both-scope comparisons19/28 retain the rows. The frozen input is unchanged and the defect is recorded in `evaluation-defects.json`. Missing CLI in those requests cannot be blamed on a model or production source. Only separately identified post-fix diagnostic fixtures correct that authoring error.

This supports the MMQ17 finding; area/record conflict still needs its own assessment. [Cisco process-ID documentation](https://www.cisco.com/c/en/us/support/docs/ip/open-shortest-path-first-ospf/13689-17.html).

RFC2328 sections10.1/10.4 define2-Way in terms of bidirectional Hello communication and allow neighbors to remain there when no adjacency is required. Those portions of MMQ29's explanation are valid; they are not penalized. The failure is its unqualified physical/data-link certification from an authored simulation record, plus speculative topology/configuration diagnosis beyond the requested source scope. The fixture is not a physical packet capture or complete protocol state-machine test. [RFC2328 neighbor states and adjacency selection](https://www.rfc-editor.org/rfc/rfc2328.html#section-10.1).
