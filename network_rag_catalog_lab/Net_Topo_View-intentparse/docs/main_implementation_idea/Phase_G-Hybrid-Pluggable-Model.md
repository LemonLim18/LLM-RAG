# Stage 4 — Implement Gemini 3.5 as an Agentic Evidence Reasoner

Gemini 3.5 Flash-Lite is the main interpretation model for complex G5/G6 tasks.

Its role is not simply to summarize records.

It should interpret the retrieved evidence, explain technical relationships and determine whether additional information is needed.

This is the behavior I specifically want implemented.

## 4.1 Initial interpretation

After the initial reader execution, pass the relevant evidence bundle and complete original request to Gemini 3.5.

The model may:

**Option A — Answer**

The available information is sufficient.

Generate a complete, evidence-grounded explanation.

**Option B — Request more context**

The available information is incomplete, ambiguous or insufficient to establish a requested conclusion.

Propose one or more specific missing reader queries for a single bounded supplementary retrieval round.

## 4.2 Shared decision contract

Reuse existing application contracts where possible.

If necessary, introduce one small provider-neutral response contract capable of representing:

- `answer`
- `need_more_evidence`

For additional evidence requests, include:

- Registered reader name.
- Target device/source.
- Requested parameters.
- Evidence gap being addressed.
- Why the evidence matters.
- Relevant existing evidence references.
- Remaining unanswered requirements.

This must be an internal structured contract, not a user-visible JSON dump.

## 4.3 Reader invocation

When Gemini 3.5 proposes another reader, the server must validate the proposal.

Check:

- Registered reader existence.
- Approved source capabilities.
- Owner permissions.
- Current source/scenario access.
- Original user prohibitions.
- Target correctness.
- Duplicate reader calls.
- Existing evidence availability.
- Remaining request time.
- Remaining cloud quota and call budget.

If valid, execute the additional reader using the existing LangGraph and tool registry.

Pass the newly returned evidence back to Gemini 3.5.

Gemini then interprets the complete updated evidence and produces the final response.

## 4.4 One bounded supplementary retrieval round

Initially support at most one additional retrieval round.

This round may contain a small bounded set of validated reader requests when necessary for the same missing-evidence decision.

Do not implement recursive unlimited tool loops.

Do not repeatedly retrieve the same unavailable source.

Do not let a model bypass user instructions such as:

"Only tell me which checks I should perform; do not execute them."

For advice-only requests, reader suggestions remain unexecuted recommendations.

## 4.5 Handling unavailable evidence

If an additional reader is unavailable, unauthorized, unsupported or cannot finish within the remaining deadline:

- Preserve the evidence already retrieved.
- Tell Gemini which evidence remains unavailable.
- Produce the best supported explanation.
- State precisely what cannot be confirmed.
- Do not hallucinate missing observations.

The model should not be forced to invent an answer simply because the workflow expects a final explanation.

## 4.6 Cloud-call budget

Normal complex request:

1. Gemini 3.1 planning.
2. Gemini 3.5 reasoning/final answer.

If additional evidence is required:

3. One Gemini 3.5 continuation after the authorized additional read.

Maximum: three cloud inference calls for an approved complex request.

Do not count individual reader operations as additional cloud inference calls unless they actually invoke a model.

Keep every cloud call within the same overall request deadline.

No additional planner loop or unlimited repair cycle.
